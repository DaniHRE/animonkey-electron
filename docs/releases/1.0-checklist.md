## Windows identity and trust gate for a future release — research 21 Nov 2026

This gate applies to a future stable version. v1.0.1 was intentionally published unsigned; its assets and tag remain unchanged.

### What Authenticode and SmartScreen do

- Authenticode verifies the signing certificate chain and the integrity of the signed file, and lets Windows display the verified publisher identity. It does not certify that the software is safe, malware-free, or high quality, and it does not guarantee a SmartScreen warning will disappear. Signing is not required by Squirrel or update.electronjs.org.
- Microsoft Defender SmartScreen considers both publisher reputation and the reputation of the specific file hash. A new signed binary can still be shown as unrecognized. Consistent signing can allow publisher reputation to build across versions; unsigned builds have to build reputation separately for each new file. Microsoft publishes no exact reputation threshold or guaranteed timeline.
- OV and EV signatures now have the same SmartScreen reputation behavior for first downloads. Microsoft states that EV no longer bypasses SmartScreen; do not purchase EV solely to suppress the first warning. Windows policy or Smart App Control can still block files that lack a trusted signature/reputation.
- The current Electron Forge guide says Azure Trusted Signing “gets rid” of SmartScreen warnings. That statement is broader than Microsoft's current guidance. Use Microsoft's current [SmartScreen reputation guidance](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation) for user-facing expectations.

### Protecting the signing key and GitHub Actions

- **Preferred cloud-service path if eligible:** evaluate the currently listed v2.0.0 Microsoft/Azure [Artifact Signing GitHub Action](https://github.com/marketplace/actions/artifact-signing) with workload identity federation/OIDC. Microsoft's integration documentation lists GitHub Actions as a supported integration. The Marketplace action uses Windows runners and demonstrates SHA-256 file digests and RFC 3161 timestamping.
- Grant id-token: write only to the isolated signing job; keep contents: read there. GitHub documents that id-token: write only permits requesting an OIDC token and does not grant repository write access. Keep release publication in its existing separate job, with contents: write only where the upload requires it.
- Bind the Azure federated identity to this repository and the approved release ref/environment, grant only the Artifact Signing certificate-profile signer role, and use a protected GitHub environment with tag/ref restrictions and required approval where the repository plan supports it. Do not make signing credentials available to pull requests, ordinary CI, or arbitrary release/** pushes.
- Pin the third-party signing action to a reviewed full commit SHA. Review its source and updates before changing that pin.
- Do not place a private key, exportable PFX, PFX password, or long-lived Azure client secret in the repository, package, or workflow. OIDC uses short-lived workload identity. Tenant/client/subscription identifiers may be needed to configure the identity; any GitHub/Azure credential or secret change requires a separate authorization.
- For a traditional OV/EV certificate, use the CA's approved hardware token, HSM, or remote signing service. Do not copy a private key to a hosted runner. Confirm that the signing provider is supported by the selected Electron Forge/@electron/windows-sign integration and that the runner can access it securely.

### Files to sign and verification sequence

- Sign the downloadable Setup.exe and the installed Animonkey.exe. Review every PE file that ships inside the Squirrel package, including Animonkey_ExecutionStub.exe, squirrel.exe, the native wreq-js module, and app/runtime DLLs. Sign application-owned or rebuilt PE files; preserve and verify valid upstream signatures such as the Microsoft-signed d3dcompiler_47.dll and dxil.dll. The 10 unsigned package paths are listed in the v1.0.1 artifact audit and form the concrete review set for a future candidate.
- Electron Packager supports signing packaged Windows binaries through packagerConfig.windowsSign. Electron Forge's Squirrel maker supports Windows signing options for the installer; see the [Forge Windows code-signing guide](https://www.electronforge.io/guides/code-signing/code-signing-windows), [Squirrel.Windows maker options](https://www.electronforge.io/config/makers/squirrel.windows), and [Packager Windows signing options](https://packages.electronjs.org/packager/v20.2.0/interfaces/Options.html). The current repository config has no signing integration; this research does not implement or validate one.
- **Unproven integration boundary:** the current workflow runs `pnpm make` in one step, and the project pins Electron Forge 7.11.2. Forge's CLI documents `make --skip-package`, so a future non-publishing prototype could separate `package` from `make`: an external OIDC signing step could sign selected PEs in the packaged app before Squirrel creates the `.nupkg`. This alone does not cover executables generated or added by Squirrel, nor prove that the Microsoft Artifact Signing Action can be called from Forge's maker hooks. The Squirrel maker and `@electron/windows-sign` expose custom signing hooks, but compatibility with the exact locked versions and Azure OIDC flow must be demonstrated. Prototype the entire path, including the Squirrel helpers and Setup.exe, and verify the regenerated final package and `RELEASES` before adopting it. Do not sign files inside an already-created `.nupkg`.
- Sign packaged application PE files before Squirrel seals them into the full .nupkg, then sign the final Setup.exe. Do not mutate PE files inside a completed .nupkg without rebuilding that package and regenerating RELEASES: the manifest's hash and size must describe the final signed package.
- The .nupkg is a ZIP/NuGet container and RELEASES is a plain-text Squirrel manifest; neither is an Authenticode PE file. Verify their published SHA-256 digests and verify all intended signatures on the PE files inside the extracted .nupkg.
- Use SHA-256 for the file digest and RFC 3161 timestamping with SHA-256. Microsoft's current examples use /fd SHA256, /tr with an RFC 3161 timestamp URL, and /td SHA256. A trusted timestamp can keep a signature verifiable after the signing certificate expires when the signature was valid at the timestamp; it does not guarantee SmartScreen reputation.
- On a Windows verification runner, run SignTool with the Authenticode policy for every expected signed PE, for example: signtool verify /pa /all /tw /v Animonkey-setup.exe. Also record Get-AuthenticodeSignature status, signer subject, certificate chain result, digest, and timestamp. Run this against the final downloaded release assets, extract and verify the .nupkg contents, and compare the GitHub asset digests plus the Squirrel RELEASES hash/size to the final package.

References: [Microsoft SignTool](https://learn.microsoft.com/en-us/windows/win32/seccrypto/signtool), [Authenticode timestamping](https://learn.microsoft.com/en-us/windows/win32/seccrypto/time-stamping-authenticode-signatures), [Forge CLI make and `--skip-package`](https://www.electronforge.io/cli), [Squirrel.Windows signing options](https://js.electronforge.io/interfaces/_electron_forge_maker_squirrel.InternalOptions.SquirrelWindowsOptions.html), [`@electron/windows-sign` custom hooks](https://packages.electronjs.org/packager/v20.2.0/interfaces/PackagerWindowsSignOptions.html), and [Squirrel.Windows output files](https://www.electronforge.io/config/makers/squirrel.windows).

## Product decisions and operational state

- **Windows signing for v1.0.1:** the user chose unsigned distribution because no publisher identity was verified and no certificate was configured. Authenticode is not required by the Squirrel update feed. The absence of a signature can lead to SmartScreen/reputation prompts or blocking under Windows policy. Do not invent a publisher identity.
- **Stable channel:** main is the production source; Windows x64 distribution uses GitHub Releases. A main push produces CI; a stable SemVer release reachable from main supplies the updater assets. Other operating systems/channels are outside initial 1.0.
- **Auto-update:** Electron autoUpdater with update.electronjs.org consumes public stable SemVer releases. Checks run only in packaged Windows x64; downloads run in the background and the app offers restart. User screenshots confirm the 1.0.0-to-1.0.1 flow; rollback is not covered.
- **Pipeline:** .github/workflows/release-windows.yml validates and builds on pushes to main or release/**. A validated published stable release attaches Setup, RELEASES, and the full package. Runs [44857046242](https://github.com/DaniHRE/animonkey-electron/actions/runs/44857046242), [44858239651](https://github.com/DaniHRE/animonkey-electron/actions/runs/44858239651), and [44859562985](https://github.com/DaniHRE/animonkey-electron/actions/runs/44859562985) passed on the release branch; the last includes the immutable icon URL. The v1.0.1 release and stable-channel assets were subsequently published as recorded above.
- **External monitoring:** no external monitoring service for initial 1.0; review providers/contracts manually. Reconsider alerting after release operations and usage justify its cost.
- **Embed CSP:** for 1.0, frame-src https: accommodates dynamic provider hosts. The player validates HTTPS URLs, and the renderer has no Node access or generic IPC. Keep this residual documented and reconsider when a stable trusted host list exists.
- Additional systems/architectures, direct web-profile import, and AniZip enrichment are conditional. Watch Together, admin, institutional pages, and web metrics remain outside the desktop scope.
