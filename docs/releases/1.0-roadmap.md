# Animonkey 1.0 — release roadmap

This document organizes the remaining work toward 1.0. It is a plan, not a publishing workflow: CI, artifact hosting, auto-update feeds, and changelog automation are deliberately deferred to a later, separately reviewed stage.

The migration is complete. The [release checklist](./1.0-checklist.md) is the current evidence ledger; this roadmap defines the order in which its open gates should be handled.

## Release stages

### 0. Repository presentation and hygiene

- Establish the official Animonkey mark and generate platform icon files from its vector source.
- Keep the primary README in English and provide a linked Brazilian Portuguese version.
- Add genuine screenshots from the packaged app, using a clean local profile and no personal data.
- Move historical migration documents into `docs/archive/`; keep active release evidence in `docs/releases/`.
- Review tracked files, ignore rules, links, license, package metadata, and GitHub description/topics.

**Exit:** README links and screenshots work on GitHub, documentation has one clear home, and generated/local files are not accidentally tracked.

### 1. Freeze the 1.0 release candidate

- Choose the first supported distribution target and record its operating system, architecture, Node/pnpm versions, and artifact format.
- Build from a clean checkout on Node 26; record the commit and verify that each expected artifact is new and complete.
- Install in a disposable Windows Sandbox or VM. Verify a clean install, upgrade from the previous build, rollback/recovery, uninstall, and preservation of local data.
- Exercise the release flows in the checklist, including account-free usage, network/process failures, and recovery.
- Complete the audiovisual matrix for providers and formats that are actually available. Do not infer audio, caption, chapter, or provider support from a successful package build.

**Exit:** every required 1.0 gate has reproducible evidence tied to the same candidate commit and artifact.

### 2. Close product, legal, and distribution decisions

- Confirm the supported platforms and initial download channel.
- Decide the Windows signing identity and how unsigned builds will be described if signing is deferred.
- Review third-party notices, licenses, privacy/data handling, CSP origins, permissions, IPC boundaries, and packaged fuses against the exact candidate.
- Decide whether 1.0 has auto-update. If yes, define signed metadata, hosting, rollback, and channel isolation before implementation.

**Exit:** the release owner has resolved every open decision in the checklist; unresolved choices are explicit 1.0 exclusions.

### 3. Approve channel and version policy

Use semantic versioning for shipped builds:

| Purpose              | Version example | Audience                                                                     |
| -------------------- | --------------- | ---------------------------------------------------------------------------- |
| Experimental preview | `1.0.0-exp.1`   | Opt-in testers; may be unstable and must not replace stable data or updates. |
| Development build    | `1.0.0-dev.12`  | Internal/early testers; built from `develop`.                                |
| Beta                 | `1.0.0-beta.1`  | Broader preview after the candidate gates are close.                         |
| Release candidate    | `1.0.0-rc.1`    | Final validation; promote the same source commit when accepted.              |
| Stable               | `1.0.0`         | Main public release.                                                         |
| Compatible fix       | `1.0.1`         | Stable patch update; no unrelated feature work.                              |

Do not let experimental or development builds subscribe to the stable update channel. Keep channel configuration and user data isolated so a preview cannot silently overwrite a stable installation. Decide the updater and artifact-feed details in stage 4; do not infer them from version strings alone.

### 4. Design and implement release automation later

Only after stages 1–3 are accepted, design the production build, signing, artifact storage, update channels, changelog generation, and release workflow. Keep each concern in a separate reviewable change. Preserve the existing Node 26 build requirement and verify artifact freshness instead of trusting a successful process exit alone.

This stage is intentionally not implemented by the current repository polish task.

### 5. Publish 1.0 and maintain patches

- Publish only after the final checklist is green and the signed (or explicitly unsigned) candidate is the one that passed validation.
- Tag the exact stable commit as `v1.0.0`; publish notes and checksums for the artifacts actually released.
- Track incoming defects against `1.0.x`; ship security and correctness fixes as `1.0.1`, `1.0.2`, and so on.
- Plan `1.1.0` for compatible features and `2.0.0` only for intentional breaking changes.

## Branch model

- Keep one explicit objective per working branch. Once complete and reviewed, merge it into `main` for approved stable work or `develop` for ongoing integration; verify the merge, then close/delete the branch locally and remotely as described in [CONTRIBUTING.md](../../CONTRIBUTING.md).
- `main` is the stable line. Do not commit directly; merge reviewed release candidates and patch fixes.
- `develop` is the integration line for the next development build. Promote only reviewed changes from short-lived `codex/feat-*` and `codex/fix-*` branches.
- `experiment/<topic>` is temporary and opt-in. Do not publish it as stable or merge it without a review of its data, security, and update-channel effects.
- `release/1.0.x` is temporary stabilization work. Freeze scope, accept only release fixes, and merge accepted changes back into `develop` after promotion.
- Use `release/1.0.0` for the initial 1.0 candidate; create `release/1.0.x` only when the patch line exists.

Promotion path:

```text
codex/feat-* or codex/fix-* ──PR──> develop ──> dev channel
experiment/<topic> ──review/adopt──> develop
develop ──scope freeze──> release/1.0.0 ──> beta / rc
release/1.0.0 ──accept same commit──> main ──tag v1.0.0──> stable
hotfix/1.0.x ──PR──> release/1.0.x and main ──tag v1.0.n──> stable patch
```

Keep the branch model lightweight: feature and experiment branches are short-lived; only `main` and `develop` are permanent. Do not create release automation or long-lived channel branches until the update-channel decision is approved.

```text
Prepare Animonkey Electron for its first public 1.0 release. Work through the stages in docs/releases/1.0-roadmap.md and use docs/releases/1.0-checklist.md as the evidence ledger.

Start by reading AGENTS.md, the archived migration plan only when historical context is needed, the current checklist, package metadata, and the relevant implementation. Inspect git status, branch, and diff before changing files. Preserve all unrelated local files and never modify the sibling website or the Anivexa submodule contents from this repository.

Work one reviewable stage at a time. Before each stage, state its scope and acceptance criteria. Implement only that stage, run the proportional checks, inspect the complete diff, update AGENTS.md when new repository rules are learned, and update the checklist with evidence, limitations, validation, and the next step. Commit each coherent completed stage locally with a Conventional Commit. Do not push, publish, sign, change GitHub settings, or modify release infrastructure unless that specific stage explicitly authorizes it.

The current build target is Node.js 26 and pnpm 10. Keep the yauzl 3.3.1 override required for Electron ZIP extraction. A build is successful only when the expected fresh artifacts exist and their timestamps match the candidate build. Do not treat a compiler exit code as evidence of runtime, installation, media, or release parity.

For player and Electron security acceptance, use a packaged build and the evidence required by AGENTS.md. Keep personal account data, credentials, private provider payloads, and unsigned test secrets out of screenshots, logs, documentation, and commits. Do not use computer control unless the user explicitly authorizes that work in the current task.

Do not implement production publishing, auto-update, or changelog automation while preparing repository presentation or release evidence. First complete the current stage and present its concrete result; then continue to the next roadmap stage.
```
