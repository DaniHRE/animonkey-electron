# Animonkey v1.2.0 Release Candidate

## Status

Version 1.2.0 is the proposed next minor release after v1.1.0. The backwards-compatible action-feedback and notification-center features add user-facing behavior and fit a minor version increment. Distribution remains Windows x64 through the existing unsigned Squirrel.Windows workflow.

This candidate is under development on `feat/discord-disc-36-toast-feedback`, based on `dev` at `367c444`. It has not been merged, pushed, tagged, installed, or published. A local Windows x64 Squirrel package was built and verified for QA; it has not been installed or distributed. The candidate is not approved for production promotion.

## Candidate scope

- Immediate action feedback for meaningful success, refusal, and failure outcomes.
- A local action-history category that remains until users explicitly delete entries.
- A floating notification center with independent action, system, anime/episode, and update categories.
- Motion transitions for toast stacks and the notification panel, with reduced-motion and keyboard support.
- Existing local episode alerts, update notifications, and best-effort remote-feed behavior.

GitHub issue [#9 — Refactor notifications and provide feedback for user actions](https://github.com/DaniHRE/animonkey-electron/issues/9) complements the newest Discord request catalogued as DISC-36 in [the feature backlog](../discord-feature-backlog.md).

## Known limitations and operational checks

- Action feedback is stored in the local IndexedDB notification store and is kept until the user deletes it. Other notification kinds retain their existing bounded retention and remote-feed expiry behavior.
- Action records are local to the current profile and are not included in account synchronization or account exports.
- The development and packaged panels have been visually reviewed, including category typography, anime poster/title/relative-time details, and mark-all placement. Runtime verification covered the success path and persisted read history. Concurrent toast timing, refusal/error outcomes, history deletion, and installed-app update behavior remain unverified; static checks do not establish those cases.
- The application installer remains unsigned under the established distribution model.
