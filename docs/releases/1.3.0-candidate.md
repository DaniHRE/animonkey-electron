# Animonkey v1.3.0 Release Candidate

## Status

Version 1.3.0 is the next minor release after v1.2.0. It includes the profile-image refresh fix from GitHub issue [#10](https://github.com/DaniHRE/animonkey-electron/issues/10) and a refreshed embedded Anivexa runtime with an updated provider inventory.

The candidate is being prepared on `release/1.3.0`, based on `dev` at `8d17010`. On 2026-11-26, the repository owner authorized integrating the candidate into `dev`, promoting it to `main`, creating tag `v1.3.0`, dispatching the Windows stable-release workflow, and publishing the resulting release after applicable validation.

## Candidate scope

- Refresh the shared account session after uploading or removing an avatar so all views show the current image immediately.
- Update the embedded Anivexa runtime from `fb337ea` to `c9e0b72`.
- Replace the retired MKissa and Senshi provider entries with AniHQ and Pahenime.
- Include the AniPM domain fix and AnimeGG/AniKoto catalog matching fixes from the upstream runtime.
- Update provider labels, monitor samples, and provider-failure allowlists to match the current runtime.

## Known limitations and operational checks

- The connected Supabase project still records a mismatched migration history. Do not run `supabase db push` until the authoritative baseline and history are reconciled, as documented in [Supabase deployment status](../supabase-deployment.md).
- Migration `20261126194708_update_anivexa_provider_allowlists.sql` and the updated `desktop-api` function have not been deployed to the connected project. The scheduled health monitor will need the updated provider constraint before it can write snapshots for the current inventory; provider-failure reports for new provider IDs also need the function update.
- The connected Supabase project is the only available project in the current account and its migration ledger differs from this checkout. No non-production database was available for applying and validating the migration.
- The avatar flow was not manually exercised in an authenticated profile, and live playback was not checked against upstream providers.
- Provider integration checks against live upstream sites were not run as part of this release preparation.
- The Windows installer remains unsigned under the established distribution model.

## Promotion path

After candidate checks and the backend deployment path are resolved, integrate the release commit into `dev`, promote `dev` to `main`, create `v1.3.0`, and dispatch `.github/workflows/release-windows.yml` from `main`. The workflow validates and builds the tagged Windows x64 package and creates a draft GitHub Release with the verified assets. Publish the verified draft only after the workflow succeeds.

Close issue [#10](https://github.com/DaniHRE/animonkey-electron/issues/10) after v1.3.0 ships.
